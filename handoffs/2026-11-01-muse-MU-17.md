## 1. The four kinds and what one tree is made of

Kind is picked at scatter by height/moisture/slope (`treeKindFor`, index.html:18213): **pine** (alpine band, dry slopes), **oak** (wet), **autumn** (dry), **birch** (the fallback mix). Every tree is *grown individually* — `growTree` builds a unique shape per tree from its seed ("every tree being its own shape is the point; 430 trees take a few hundred ms", index.html: buildTreeMeshes note). There is no shared per-kind geometry today; that is the GPU forest's first change, and it changes the look (a forest of 4–8 template shapes, varied by scale/lean/colour, vs 430 uniques). Parts per tree (`buildTreeMeshes`, index.html:17896):

- **Trunk + branches:** one merged vertex-coloured mesh (`trunkMesh`, `accToGeometry(T.wood)`, treeWoodMat; cast+receive shadow). Branches are folded into it deliberately ("Part of the trunk's mesh (one draw fewer a tree)").
- **Crown wood** (pines/broadleaf cores): a second wood mesh when it has geometry (`crownWoodMesh`, may be null).
- **Canopy:** leaf clumps (oak 13, autumn 12, birch 10 + a core clump; pine its cones) merged into **one geometry per tree** with per-piece vertex ranges remembered (`mergeCanopy`) — one draw, down from 5–8 blob draws (the 2,612-of-6,600-meshes problem, index.html: canopy comment). Per piece: centre, range, colour (one main colour per tree, clumps drift; autumn tops turn first). Legacy mode (`?canopy=legacy`) restores per-blob meshes.
- **Materials: exactly two, shared by every tree** — `treeCanopyMat`, `treeWoodMat` (index.html:17534), node/TSL builds with a wind sway `positionNode` and an ember/fire term (`buildTreeShaders`, index.html:17530ff; flat `MeshStandardMaterial` fallback, index.html:17544). This is the forest's best friend: **one material per part already** — instancing changes geometry delivery, not pipelines.

**Draw cost.** Live: **2–3 draws per tree** (trunk, crown wood if any, canopy) — about 860 tree draws before batches (index.html: tree-batch comment, index.html:18040ff). Batched: **2 draws per 64 m cell** (one wood, one canopy, MU-13 §2.4), the tree's own meshes hidden, matrices frozen, canopy baked *at rest* (no sway in the copy — `tbWrite` zeroes canopy rotation). Shadow cost is live-only by design (`castShadow = false` on batch meshes; shadows stay with live trees inside SHADOW_NEAR).

## 2. The lesson already learned about instancing here

The canopy comment (index.html, merged-canopies block) records it: an InstancedMesh-per-canopy attempt was **backed out on a real GPU** — three's WebGPU renderer built one instance-matrix uniform buffer per *program*, so structurally identical canopies drew with the first tree's matrices/colours ("orange autumn crowns floating over birches"), invisible to the headless harness. Whatever the GPU forest uses (instanced buffers per kind, indirect draws), its first test must be two kinds interleaved at distance, on the GPU — that failure mode is exactly "looks fine up close, wrong at range". Point Claude at GP-19996's vendor findings for whether r175 still behaves that way for InstancedBufferAttribute-driven meshes (the batch cells, which are plain merged meshes, never hit it).

## 3. Per-tree state after load: what changes, who reads it

The authoritative list is `tbSnapshot` (MU-13): 20 fields — alive, falling, stump, log, leafHealth, health, burnT, smoulder, trimStage, canopyTransparent, group.visible, parent, position xyz, rotation xyz, canopy scale, leafHiddenCount. By cause:

- **Sway:** canopy wind in the material (phase per tree via vertex/leaf data; live only — batched copies are at rest). Reader: nobody in JS per frame except the fade/batch checks that treat rotation as state.
- **Damage/trim:** `damageTree` (index.html:52191) hides leaf pieces by health share (piece ranges collapsed in the merged canopy), trims stage, chunk spawns at piece positions. Chainsaw and rounds both land here (MU-14).
- **Felling:** `beginTreeFall/updateFallingTrees` (index.html:52608/52780) — the group animates, then stump + a log solid (MU-14); `restoreTree` reverses it for batch rejoin.
- **Burning:** `igniteTree/updateBurningTrees` (index.html:52292/52368) — per-piece burn progress, ember attribute, smoulder; spreads ground fires; the wood/canopy materials carry the fire term (why the shader build exists).
- **Fades:** `updateTreeFade` (index.html:54227ff) — canopy transparency near the player/camera line (keeps the marine visible); sets `canopyTransparent`, which alone keeps a tree out of its batch (MU-13).
- **batch/live swap** itself (MU-13 §2.4): distance (live inside ~46 m), any snapshot change, swaps capped 12/frame.

Every one of these is a *discrete event or a local animation* — none needs per-frame CPU on a far tree, which is why the batch system works. The forest equivalent: per-instance state flags the compute pass can test (alive/stump/burning/fade) with the *effects* (fall animation, piece shedding, fire) still handled by promoting that instance to a live unique tree — i.e. keep today's live-tree path as the "hero" path inside the near/shadow square, exactly where batching already keeps trees live.

## 4. What the instanced forest keeps per instance — and drops

**Keep per instance:** transform (position, yaw, scale — lean is baked in the grow today; per-instance lean needs either a tilt in the instance matrix or it becomes kind-template lean), kind (selects the template), a colour tint (today's per-tree main colour, autumn gradient is per-clump — a per-instance tint + the template's baked gradient approximates it), health/state flags (standing / stump / felled-log / burning with a burn phase), leaf-health share (drives how much canopy the card/LOD shows — or drop to standing/stripped two states), canopy radius/height (CU-196's sightline reads these from `TT.trees` today: canopyRadius, canopyBottom, canopyTop — keep them as data even if the mesh is a card).

**Drop:** unique geometry per tree (the 430 unique grows — build time and memory go with it), leaf *pieces* (per-clump ranges exist for damage shedding; at forest scale, damage becomes per-instance health states + the near-tree live path keeps pieces), crown-wood as a separate draw (fold into the kind template's wood mesh: live cost goes 3→2), per-tree group hierarchy (groups, frozen matrices, `walkSkip` bookkeeping all go), the snapshot diff itself (state becomes flags written on events).

**Cards for far trees:** a card needs kind, tint, and canopy silhouette — the template canopy's projected shape is enough; today's far look is already a merged low-poly canopy at rest with no shadows, so a crossed-card LOD past the batch's current range is a *smaller* step than the batch was. The joins to design: (a) near→instanced and instanced→card transitions must not pop colour (tint continuity), (b) a far tree that catches fire/falls must promote without a hitch (the 12/frame swap budget is the precedent).

## 5. Shadows, minimap, tests

- **Shadows:** live trees cast (trunk/crown/canopy, index.html:17896ff); batched don't; the shadow square (SHADOW_NEAR 42 m, index.html:54551) decides which are live. A GPU forest keeps this split for free if near trees stay live-unique; instanced trees inside the shadow square casting correctly is a renderer question (caster pass with instancing — GP-19996 territory). Canopy shadow *scan* (index.html:54564: 60 trees/frame round-robin reading canopy extents for shadow/cover purposes) reads tree data, not meshes.
- **Minimap:** its ground bake doesn't draw individual trees — trees reach "the map" through data reads (`TT.trees` canopy fields for CU-196's sightlines; canopy cover % of the floor). The forest must keep the *data* (position, kind, canopy metrics) even where it drops meshes, or CU-196/W1's tests lose their input. Same for `distToPath`-style readers in MU-14: they read the trees array, which must survive as a data table (position/kind/state) with meshes derived.
- **Tests that count or place trees:** t50 (tools/tests/t50.js:19,25 — batched share > 60%, tree draws < half the tree count: both bars are about *today's* mechanism; a forest that draws 1-per-kind passes the spirit and fails the letter — that's a rule-13 --review conversation, not a silent edit), the batch-stats readers (`TT.treeBatchStats`, index.html:18302), tests that pick a tree to stand by/fell/burn (they read `trees[]` and the live path — keep both working), and MU-12's hikers'-tree/Pike searches (position readers, MU-14). Also `?trees=single`, `?canopy=legacy`, `TREES_FORCE_FLAT` A/B switches (index.html:17536ff) — the forest needs its own `?forest=0`-style fallback to today's path, per CL-288's "switches back" rule.
