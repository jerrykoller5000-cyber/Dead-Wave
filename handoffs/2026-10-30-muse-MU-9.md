## The list, worst first

1. **`ui/objectives-runtime.js:36` `update()` — 10 Hz for the whole fight (NEW file in 1.1; mounted from [index.html](/mnt/c/Users/Zero/Desktop/Tiny Trek/index.html:31076) `updateKioskPrompt`, CL-263/CL-184).** Its rAF `poll` calls `update()` every 100 ms unconditionally. Each call allocates: `OBJECTIVE_IDS.map(id => ({id, prop, interaction}))`, a `.filter().sort()` near-list, `model.snapshot()` (twice, three times on a claim), `sites: facts.map(f => ({...}))`, a display object whose `sites.map` builds `{...site, position:{x,z}, choices: opts.map(...)}` per site, then `JSON.stringify({...display, sequence:0})` just to compare with `lastPaint`. The page side `getObjectiveInteraction`/`getObjectiveProps` run per site per call on top. Guess: 3–8 KB per call × 10/s ≈ **30–80 KB/s**, the largest steady new churn in the fight, and it runs even when nothing objective-related can change (mid-wave, player nowhere near a site). Cheap fix: skip `update()` while `phase==='night'` and no site is reachable (or drop to 2 Hz then), build the signature from scalars instead of `JSON.stringify` of the whole display, and reuse one scratch `facts`/`display` structure.

2. **Flight recorder, CU-160 (NEW) — [index.html](/mnt/c/Users/Zero/Desktop/Tiny Trek/index.html:59536) `flightRecord(dt)`, called every frame from `tick` ([index.html](/mnt/c/Users/Zero/Desktop/Tiny Trek/index.html:60671)).** `flightLog.fill({t, dt, keys, …})` allocates one ~28-field object per frame (the recorder itself, [flight-recorder.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/core/flight-recorder.js:91), is exemplary: typed ring + reused scratch — the waste is only the caller's literal). ~500 B × 60 ≈ **30 KB/s**. Every 5 s `flightTakeSnap()` ([index.html](/mnt/c/Users/Zero/Desktop/Tiny Trek/index.html:59393)) allocates a `zombiesNear` array + one `{type,x,y,z,yaw,hp}` per zombie within 60 m (capped by `.slice(0,64)`), `quest.read()` ([story-chain.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/story-chain.js:89): `leads.map(l => ({...l, ...s(l.id)}))` + two filters + `log.slice()`), three `JSON.parse(JSON.stringify(...))` deep copies (relay state, magazines, ammo), `flightBones()` (one array per marine bone), plus `{...POSE}`, `{...bodyRecoil}`, `{...marineIdle.state}` spreads. Guess 20–60 KB per snap. Cheap fix: fill the recorder's scratch from scalars (a `fillScalars(...)` or write fields onto a reused sample object); for snaps, reuse the arrays/objects or accept — 5 s cadence makes it minor except as a GC-spike suspect (below).

3. **Turrets: [index.html](/mnt/c/Users/Zero/Desktop/Tiny Trek/index.html:54213) `turretAimPoint(b,z)` + [index.html](/mnt/c/Users/Zero/Desktop/Tiny Trek/index.html:54189) `turretMuzzle(b,ang)` (CU-116/CU-165 comments) — per turret × per zombie, every frame.** `updateTurretsInner` loops every alive zombie for every firing turret; each candidate inside the running best distance calls `turretAimPoint`, which allocates a muzzle `{x,y,z}` and, on the first clear height, the returned `{x,y,z}` (up to 3 `turretShotBlocked` walks over all builds per call). Worst case ~4 turrets × 48 zombies ≈ 190 calls/frame; realistically far fewer pass the distance gate. Guess **10–100 KB/s** depending on turret count. Per turret shot it also news two `THREE.Vector3` (origin/dir, [index.html](/mnt/c/Users/Zero/Desktop/Tiny Trek/index.html:54382)) — trivial at turret fire rates. Cheap fix: write muzzle/aim into per-turret scratch objects (`b._muzzle`, `b._aim`) and return a boolean + height index.

4. **Screamer arms: [screamer-behavior.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/screamer-behavior.js:95) `applyScreamerPose` (GP-19971) — per screamer, per frame.** The new independent arm loop is `for (const [i,arm] of [u.armLG,u.armRG].entries())`: one 2-slot array + one iterator + destructuring per screamer per frame. A handful of screamers at night 20 ⇒ **~5–20 KB/s**. (The older leg loop just above uses the same pattern but is unchanged 1.0 context — not counted; fixing both is the same one-line change.) Cheap fix: two unrolled iterations or a module-level `ARMS` scratch pair looped by index.

5. **Shambler recovery: [shambler-recovery.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/shambler-recovery.js:35) `shamblerRecoveryStep(z)` (GP-19853/GB-241) — per recovering shambler, per frame.** Every return path news a `{x,z,pace}` object (4 return sites). ## On the 25 MB GC at frame ~1300 and the 39.6 lows

The steady new churn above sums to roughly **50–200 KB/s**, i.e. ~1–4 MB over the first 1300 frames — an order short of a 25 MB collection, and smooth churn does not by itself make 25–42 ms spikes. So the spike is most likely a burst, and these are the new-in-1.1 bursts near ~21 s into a night-20 fight for CU-184's `--alloc` run to confirm or clear, in my order:

1. A spawn wave: pooled zombie builds still run the new look code per (re)spawn (`refineZombieFace` closures/maps, `prepareScreamerAppearance`'s Set/Map/Colors, brute armor color table build in [brute-armor.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/brute-armor.js:8)) — watch allocations inside `spawnZombie` and the fidelity/appearance builders at wave boundaries.
2. `flightTakeSnap()` (every 5 s; frame ~1300 is a snap boundary at 60 fps): the three `JSON.parse(JSON.stringify(...))` copies scale with magazine/ammo state.
3. First demon/colossus/spitter casts of the fight (ability runtime warm-up: `acidBatch()`, `shotMesh`, `primeVisuals` leftovers) — one-time, but they land mid-fight in 1.1's new ability mix.
4. The objectives `update()` at 10 Hz (item 1) coinciding with a frame — small, but it is the only new timer that fires all fight long.

If CU-184's allocation profile disagrees with items 1–8, believe the profile; this map's job was to give it names to look for.
