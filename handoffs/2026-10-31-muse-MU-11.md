## 1. What holds (checked against r175, do not re-litigate)

- **The two depth conventions are both right.** [viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:39) takes `zMin` from `renderer.coordinateSystem`, which in r175 is a getter for the backend's system ([three.webgpu.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/vendor/three/three.webgpu.js:50120)): 2000 (WebGL) → −1, else 0. The hand-built projection ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:52)) matches `Matrix4.makePerspective` term for term in both branches ([three.core.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/vendor/three/three.core.js:12141)): WebGL `e[10]=(f+n)/(n−f)`, `e[14]=2fn/(n−f)`; WebGPU `e[10]=f/(n−f)`, `e[14]=fn/(n−f)`. The depth press ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:43)) then maps WebGL z∈[−w,w] to [−w,−0.92w] and WebGPU z∈[0,w] to [0,0.04w] — the front 4 % from the near plane on both backends, as designed.
- **The MVP override lands where r175 calls it.** `NodeMaterial.setupModelViewProjection(builder)` returns `cameraProjectionMatrix.mul(positionView)` ([three.webgpu.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/vendor/three/three.webgpu.js:17538)) and is invoked through `builder.context.setupModelViewProjection` ([three.webgpu.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/vendor/three/three.webgpu.js:17289)). Assigning `m.setupModelViewProjection = vmMVP` as an own property after the clone ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:64)) therefore shadows it for exactly that material; `vmMVP`'s `projU.mul(TSL.positionView)` has the same shape as the default. The `|vm281` program-cache suffix ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:65)) keeps view-gun programs from colliding with the same material's world programs. Writing the uniform's matrix elements in place ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:53)) is safe: r175 uniforms upload from `.value` when the node updates, so ADS FOV and aspect changes are live.
- **The eye-hide filter coexists with r175's own function swaps.** The filter signature matches the r175 callback including `passId` ([three.webgpu.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/vendor/three/three.webgpu.js:51483)), and the renderer consults the current function at each `render()` ([three.webgpu.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/vendor/three/three.webgpu.js:50570)), so the scene PassNode's render obeys it. The shadow pass saves the current function, installs its own with `scene.overrideMaterial`, and restores afterwards ([three.webgpu.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/vendor/three/three.webgpu.js:38045)) — his eye-hidden arms and gun therefore still cast their shadows, as the stage-1 handoff intends, and the view meshes (`castShadow = false`) never enter the shadow map. The outline node's identical save/restore ([three.webgpu.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/vendor/three/three.webgpu.js:33891)) composes the same way.
- **Hip and ADS frames agree.** `BORE_AHEAD` (π about Y, [viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:248)) and the ADS basis built from the sight line ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:396)) are the same convention (bore → view −z, up → +y, determinant +1 — a rotation, not a mirror), so the hip↔ADS slerp takes the short way. The rear-sight swap `notch → (0, notch[1], notch[0])` ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:404)) is correct against the data: `pistol: notch: [-0.064, 0.082]` is [z, y] in gun space ([sight-points.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/sight-points.js:9)). The spring integrator substeps at 240 Hz ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:275)) — stable at k=240–260 — and `poseArm`'s wrist composition is exact (root then wrist multiply back to W.q, net hand scale W.s; [viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:357)).

## 2. Findings, worst first

1. **MEDIUM — The gun's whole subtree is traversed twice a frame to prove nothing changed.** `setEyeHide` builds its stamp with `countNodes(gunSrc)` ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:128)) and `setEyeHide` runs every frame ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:485)); `update` then traverses again for the same count ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:488)), plus a stamp string per frame. Sure: code fact. Cost scales with gun nodes (the pistol is small; stage-4 heavies won't be). Fix: count once, cache it, and re-count at 5–10 Hz or when a builder dirty-flag says the gun changed; build the stamp from the cached count.
2. **MEDIUM — A geometry swap on his gun never reaches the copy.** `cloneLean` shares `src.geometry` once at build ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:184)); `mirrorParts` then mirrors only transform and material ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:462)), and the rebuild check counts nodes, not geometry (finding 1). If a stage-2+ builder swaps `mesh.geometry` in place (a suppressor fitted, a magazine variant — GP-19986's real-size magazines are exactly this shape), the view gun keeps the old geometry until the node count happens to change. Sure: code fact; whether any current builder swaps geometry is outside these files. Fix: one reference compare per pair in `mirrorParts` (`if (o.geometry !== s.geometry) o.geometry = s.geometry;`) — no allocation, catches it the same frame.
3. **MEDIUM — The magazine and slide maths assume both are direct children of the gun root.** `footOf` converts the magazine's bounds through `gun.mag.matrix` (its parent-local matrix) as if that were gun space ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:315)), the slide grab does the same ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:296)), and the palm ride writes `gun.mag.position` directly ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:517)). Any transformed subgroup between the gun root and either part offsets the foot, the grab and the riding magazine by that subgroup's frame. Sure: the assumption is in the code; the pistol's builder structure is outside this task's files, so I cannot say it is breached today. Fix: either convert through the parent chain (`parent.matrixWorld` against the copy root's inverse), or write "mag and slide are direct children of the gun root" into stage 2's table (GP-19993) as a builder requirement.
4. **MEDIUM-LOW — `cloneLean` silently un-skins and un-types the copy.** Any `isMesh` source — including a `SkinnedMesh` — becomes a plain `Mesh` sharing the geometry, with no skeleton bind ([viewmodel.js](/mnt/c/Users/Zero/Desktop/Tiny Trek/game/viewmodel.js:183)); `Line`/`Points` parts become empty groups. Fine for the rigid pistol; a stage gun with a skinned or morphed part (a sling, a belt) would freeze or vanish in first person with no warning. Fix: preserve `SkinnedMesh` (clone with its skeleton) or assert-and-log the types stage builders may use.
5. **LOW-MEDIUM — His whole marine is traversed every 30 frames while the view gun is up.** `body()` refreshes on an age counter as well as on re-bakes (game/viewmodel.js:165), and the refresh walks the marine for materials (game/viewmodel.js:156) plus per-elbow traversals for the rolled-sleeve check (game/viewmodel.js:151). About twice a second that is a full-rig walk landing on one frame — a small periodic hitch that grows with the marine, not the scene. Fix: refresh on `bakes` change only (the counter's other trigger), or spread the refresh over frames.
6. **LOW — Steady small garbage while active (~15 short-lived objects a frame).** `gunFrame` news the grip vector, the sight basis vectors and the rear-sight vector, two quaternions and the velocity vector, the offset vector and its quaternion (game/viewmodel.js:390, 397–404, 414, 419, 442–443); `mul` clones `b.p` per call (game/viewmodel.js:238, twice a frame for the wrists, more through a reload); `placeFrame` news three vectors plus the palm vector per call (game/viewmodel.js:291, 311) and `reloadHand` calls it twice a frame; `update` news the decompose scratch (game/viewmodel.js:491). At MU-9's scale this is a few KB/s — worth one scratch pass when stage 2 touches the file, not a hunt now. Fix: module-level scratch for the named spots.
7. **LOW — A missing wrist on the first active frame throws every frame.** `readSockets` returns early when either elbow wrist is absent, leaving `sockets.r/l` null (game/viewmodel.js:253–269); `update` then dereferences them in `mul(G, sockets.r, WR)` (game/viewmodel.js:504, 507) with no guard, and `updateViewmodel` catches only the constructor (index.html, the `createViewmodel` try at the CL-281 block, fresh line 48231ff). Unlikely — the rig is baked before a match — but the failure mode is a per-frame exception in the tick, not a degraded view. Fix: initialise the sockets to identity frames, or skip the hands until both exist.
8. **LOW — The elbow table and its reader disagree about what the numbers are.** game/viewmodel-poses.js describes `elbows` as "where each forearm points from the wrist (view space; a hint)" — a direction — while `poseArm` subtracts the wrist position from it, treating it as a view-space point (game/viewmodel.js:359). One of them misreads the other: as points, the elbows sit near the eye plane and the forearm's aim swings as the gun moves between hip and ADS; as directions, the aim is constant. Claude to say which was meant; fix the losing side (table comment or the subtraction).
9. **LOW — States it can be left in: sound, with two residuals.** On want-loss (ladder, swim, mortar, holster) the lowering path keeps the eye-hide on until the copy drops, then `setEyeHide(false)` clears every `vmEyeHide` flag and restores the previous render function (game/viewmodel.js:485, 103–135) — verified by reading, including the shadow-pass interplay in §1. A cancelled reload restores the magazine (`u == null` reads as seated, game/viewmodel.js:348, 528–531), and a rebuilt gun resets the shot counter guard (game/viewmodel.js:206). Residuals: (a) `dispose()` (game/viewmodel.js:575) is never called from index.html — the viewmodel lives for the page, which is benign today but means a renderer rebuild would strand its materials and its render-function claim; (b) if `update` ever throws between `setEyeHide(true)` and the end of the frame, the flags stay on — the same throw breaks the tick anyway, so this is a note, not a finding. The magazine cannot be left in the palm and the eye-hide cannot be left on through any path I could construct from these files.
10. **INFO — Material freshness is keyed narrowly.** `vmMaterial` rebuilds only on `version`, `map` or `transparent` change (game/viewmodel.js:79); colour, emissive and opacity are mirrored per frame (game/viewmodel.js:86–93), but a `defines`/`vertexColors` change without a version bump would not refresh the copy. The view materials also run with `fog = false` (game/viewmodel.js:69) and write pressed (near) depth into the scene depth buffer: any future depth-reading post effect (DOF, SSAO) will see the gun at centimetres. Both are correct for stage 1; both want a line in stage 2's notes.
