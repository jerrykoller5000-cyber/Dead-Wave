# CL-195 · Claude · The loading screen keeps moving, and no zombie sounds come through into the menu

Jerry (2026-10-14): "When we get to the deadwave loading screen it is still lagging pretty bad. And when you get to the
main menu you still hear zombie sounds."

## What his machine showed (qa/perf, the recorder from CL-192, seven launches today)

After the caracal, the title card and the loading screen were frozen in long blocks:

| when | block | what it was |
|---|---|---|
| the whole title card (3.2 s) | one task of **2.6–3.7 s** | `warmEffectPools` (~1.05 s, building 38 pooled bodies) + `compileForLiveTarget` (~2.1–2.7 s of node builds) |
| loading screen, after set A | one tick of **1.7–2.4 s** | the staged fight, `preRollFight`: every state of it, ~25 frames, in one tick |
| loading screen | 50–330 ms frames | set A and the live fight |

- **The bar** stood at 96% "Finishing up" for most of the loading screen. Then it said 100% "Ready" after set A (the load channel's last step), with the staged and live fights still to come.
- **The sound:** the game's master gain is held at 0 behind the opening (CL-192), but the warm-up still started its sounds behind it. Headless, that was 365 sources: deaths, groans, fire, blasts, gibs. At the hand-over the gain came up over whatever was still ringing. The kills land about 1.4 s before the menu, so long death takes and the reverb's tail were still sounding when the menu appeared.

## What changed

1. **Silence behind the opening (core/audio.js):** `hushBehindOpening(ctx)` wraps the game context's `createBufferSource`, `createOscillator` and `createConstantSource`.
   - While `DWOpening.active`, a source's `start()` is swallowed, and its `ended` follows at once. So nothing sounds, and the take bank's voice counts and the code that cleans up on `ended` still run.
   - The test is made at `start()`, so a node made during the opening and started after it plays normally.
   - Headless, from launch to the menu: 365 → 0 sources started behind the opening. The 4 still counted are the intro sting, which runs on its own context in opening.js. The menu's ambience still starts after.
2. **The compile in slices (index.html `compileInSlices`):**
   - The scene is compiled a few "units" at a time (the top-most drawables, each with whatever is under it). Each slice takes about 28 ms, and the browser gets a turn between slices.
   - A unit with a light under it is never hidden, so every slice sees the same lights.
   - A final pass with everything shown follows. It gets a fresh render id and `shadow.needsUpdate`, so the shadow map is drawn with every caster. Without that, the shadow pipelines (21 of them) were built synchronously by the first warm frame, because compileAsync puts the render id back after each call and only the first slice could draw shadows.
   - Headless WebGPU, against the baseline:

     | | baseline | sliced |
     |---|---|---|
     | async pipelines from the compile | 77 + 20 | 78 + 21 |
     | sync pipelines in the first warm frame | 8 | 8 |
     | compile time | 7.9 s | 6.0 s |
     | longest slice | the whole compile | 0.45 s (on a much slower CPU than Jerry's) |

3. **The pooled bodies** (`warmEffectPools`, now async) give the browser a turn every ~24 ms between bodies.
4. **The staged fight, one step a tick (index.html `preRollFight` now returns steps; `maybePreRollFromLoop` runs them):**
   - Each step sets its state up, compiles what the scene then shows in slices, and draws its frame on the next tick.
   - While a step compiles, `tick()` returns at once (`_warmPending`), so nothing can draw an object whose GPU pipeline is still being built. While the fight runs, a tick does that step and nothing else.
   - The same states are drawn in the same order. 'fresh' and 'effects' also redraw shadows in their final pass.
   - Headless WebGL, from launch to the menu: the same **180 shader variants** at the end as the baseline. The longest task was 16 s against 171 s there; SwiftShader is extremely slow, so only the ratio means anything.
5. **The bar (opening.js, opening.css):**
   - From the first slice on, the warm-up drives it through `DWOpening.warmProgress`:
     - 0–10% for the compile;
     - 12% for the first frame;
     - 12–20% for set A;
     - 20–65% for the staged fight;
     - 65–97% for the live fight;
     - 97–99% for the menu ticks;
     - 100% at `ready()`.
   - The load channel's own percentages stop moving it once the warm-up has started.
   - It grows by `transform: scaleX` with a transition, so the compositor animates it even while the main thread is busy.
