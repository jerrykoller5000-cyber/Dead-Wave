## Render bundles

- `BundleGroup` treats the group and its descendants as a WebGPU render bundle. `static` defaults to `true`, meaning its structure is assumed fixed; `group.needsUpdate = true` increments `group.version`. Its own documentation says the WebGL backend renders the group without the performance gain. [three.webgpu.js:70418–70426](../vendor/three/three.webgpu.js#L70418), [three.webgpu.js:70459–70494](../vendor/three/three.webgpu.js#L70459)
- The cache key is **group + camera**. On rendering, r175 re-records when it sees a new render context or a changed group version, recording through `beginBundle`/`finishBundle`; otherwise it only refreshes node/binding data for cached render objects before `addBundle`. The WebGPU backend records a GPU bundle and later calls `executeBundles`. [three.webgpu.js:47482–47507](../vendor/three/three.webgpu.js#L47482), [three.webgpu.js:50360–50432](../vendor/three/three.webgpu.js#L50360), [three.webgpu.js:69827–69871](../vendor/three/three.webgpu.js#L69827), [three.webgpu.js:68823–68832](../vendor/three/three.webgpu.js#L68823)
- A bundle does **not** skip every CPU scene operation: `render()` still calls `scene.updateMatrixWorld()` and `_projectObject()` on each render; traversal still checks child visibility, layers, and frustum and builds a fresh list. On cached replay, that new list is not used to select draws. It saves draw submission, not scene traversal/culling cost. [three.webgpu.js:50605–50607](../vendor/three/three.webgpu.js#L50605), [three.webgpu.js:50658–50670](../vendor/three/three.webgpu.js#L50658), [three.webgpu.js:51838–51955](../vendor/three/three.webgpu.js#L51838), [three.webgpu.js:50375–50432](../vendor/three/three.webgpu.js#L50375)
- Consequently **explicitly invalidate** when membership, child `visible`/layers/frustum eligibility, draw order, geometry/draw range, material or pipeline structure changes. `material.version` can cause `RenderObjects` refresh during a normal draw, but the cached branch skips `_renderObjectDirect()`/pipeline and geometry update, and the sole bundle re-record condition is group version or new render context. This is an inference from those paths, not a promise of automatic invalidation. Uniform/node values can refresh in cached replay; `static=true` suppresses some refresh checks, while `static=false` permits their per-render refresh but still does not force command re-recording. [three.webgpu.js:50375–50428](../vendor/three/three.webgpu.js#L50375), [three.webgpu.js:52172–52209](../vendor/three/three.webgpu.js#L52172), [three.webgpu.js:488–511](../vendor/three/three.webgpu.js#L488), [three.webgpu.js:25994](../vendor/three/three.webgpu.js#L25994)
- A custom `setRenderObjectFunction` is called from `_renderObjects` **while recording**, not on cached replay. CL-281's eye-hide callback in `game/viewmodel.js` therefore cannot dynamically filter a cached bundle; keep those meshes outside a static bundle or invalidate when their membership changes. The shadow pass replaces the custom callback with its own caster filter, then restores it, so CL-281's eye-hide filter does not apply there. [three.webgpu.js:52037–52045](../vendor/three/three.webgpu.js#L52037), [three.webgpu.js:50380–50428](../vendor/three/three.webgpu.js#L50380), [three.webgpu.js:38045–38078](../vendor/three/three.webgpu.js#L38045), [viewmodel.js:107–118](../game/viewmodel.js#L107)
- A `pass(scene,camera)` calls `renderer.render(scene,camera)` into its render target. Render contexts are keyed by scene, camera, and attachment state, so a scene pass can require its own recording even with the same camera. A shadow pass calls `renderer.render(scene, shadow.camera)` with an override material and caster-only callback, giving it a distinct camera/bundle. The final post-processing quad is separate from that scene bundle. [three.webgpu.js:33717–33720](../vendor/three/three.webgpu.js#L33717), [three.webgpu.js:28524–28560](../vendor/three/three.webgpu.js#L28524), [three.webgpu.js:38015–38024](../vendor/three/three.webgpu.js#L38015), [three.webgpu.js:38045–38076](../vendor/three/three.webgpu.js#L38045), [three.webgpu.js:70503–70510](../vendor/three/three.webgpu.js#L70503)
- `forceWebGL` or WebGPU fallback selects `WebGLBackend`; `_projectObject` only creates bundle entries when the backend has `beginBundle`, so WebGL traverses and renders the children as normal objects. [three.webgpu.js:70370–70386](../vendor/three/three.webgpu.js#L70370), [three.webgpu.js:51930–51953](../vendor/three/three.webgpu.js#L51930), [three.webgpu.js:70424–70426](../vendor/three/three.webgpu.js#L70424)

Suggested bounded experiment (WebGPU only; static set of far scenery, excluding CL-281 filtered meshes):

```js
const batch = new THREE.BundleGroup();
batch.static = false; // keep changing uniforms/node values eligible for refresh
batch.add(...stableMeshes);
scene.add(batch);
// On any structural, material/pipeline, visibility, or culling-set change:
batch.needsUpdate = true;
```

Benchmark CPU submission, total frame time, and both post-processing and shadow views. `static=false` affects node refresh, not the re-record condition. [three.webgpu.js:50375–50428](../vendor/three/three.webgpu.js#L50375), [three.webgpu.js:503–511](../vendor/three/three.webgpu.js#L503), [three.webgpu.js:70459–70494](../vendor/three/three.webgpu.js#L70459)

## Cached shadows

- `ShadowNode.updateBefore` renders when `shadow.autoUpdate || shadow.needsUpdate`, avoids a second update for the same camera/frame, and clears `needsUpdate` after an unchanged depth-texture version. `updateShadow` updates the light's shadow matrices and renders the entire scene from `shadow.camera` into the shadow map with caster filtering. [three.webgpu.js:38151–38177](../vendor/three/three.webgpu.js#L38151), [three.webgpu.js:38015–38024](../vendor/three/three.webgpu.js#L38015), [three.webgpu.js:38043–38076](../vendor/three/three.webgpu.js#L38043)
- Therefore the supported cache is **one whole map per light**: set `autoUpdate=false` after a valid initial render; set `needsUpdate=true` whenever the light, shadow camera/projection, caster or receiver-relevant occlusion changes. This game's existing sun policy already switches to `autoUpdate=false` at low intensity and requests periodic/movement redraws; it forces a redraw when new marine parts appear. [three.webgpu.js:38151–38177](../vendor/three/three.webgpu.js#L38151), [index.html:2355–2368](../index.html#L2355), [index.html:19782](../index.html#L19782)
- A cached static-caster map plus a small dynamic-caster map for the **same light** is not a stock `LightShadow` option here: `ShadowNode` creates one map for its shadow and one normal shadow filter/output path, and `renderShadow` redraws that map from the scene. Two ordinary shadow-casting lights would produce two light contributions, not combine two occlusion maps for one light. The latter is an inference from the one-map/one-filter implementation and needs a custom node/composition path or a renderer change if exact single-light shading is required. [three.webgpu.js:37719–37734](../vendor/three/three.webgpu.js#L37719), [three.webgpu.js:37900–37904](../vendor/three/three.webgpu.js#L37900), [three.webgpu.js:37939–37963](../vendor/three/three.webgpu.js#L37939), [three.webgpu.js:38015–38024](../vendor/three/three.webgpu.js#L38015)

Supported one-map policy sketch:

```js
sun.shadow.autoUpdate = false;
sun.shadow.needsUpdate = true; // first valid map
function shadowInputsChanged() {
  sun.shadow.needsUpdate = true; // next render refreshes whole map
}
```

For continuously moving casters, either refresh that map at the chosen cadence (accept temporal lag) or keep the light's `autoUpdate=true`. Bundle groups inside the shadow pass may reduce repeated draw submission for fixed casters, but do not avoid map rendering itself. [three.webgpu.js:38151–38177](../vendor/three/three.webgpu.js#L38151), [three.webgpu.js:50375–50432](../vendor/three/three.webgpu.js#L50375), [three.webgpu.js:38015–38024](../vendor/three/three.webgpu.js#L38015)
