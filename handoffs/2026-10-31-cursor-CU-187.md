## How the question was answered

**Size**, from V8: each script compiled as a module in Node with `--no-lazy --print-bytecode`, reading `Bytecode length` per function (`bytecode-sizes.json`: every function of index.html, game/, studio/, world/, ui/, combat/, core/ and three). **Tier and deopts**, from V8's own log in Chrome 156 (V8 15.6) of a night-20 bench run: `--log-code` writes every code object (Ignition `~`, Sparkplug `^`, Maglev `+`, TurboFan `*`, an `o` in front for on-stack-replacement code) and `--log-deopt` every deoptimization with its position and reason. Chrome's stdout (where `--trace-opt` writes) was not captured, even with `--no-sandbox`; the log files were. A function's deopts are found from the position in the script V8 logged. No game file was touched.

## Who deoptimizes, and why (deopt-tables.md; the 465 deoptimizations of the 150 s of fight)

| function | deopts | top reasons |
| --- | --- | --- |
| `updateZombies` (index.html) | 68 (29 distinct positions) | wrong map 23; dependent prototype chain changed 13; (unknown, lazy) 13 |
| `zombieLateStep` (index.html) | 32 (19 positions) | wrong map 22; insufficient type feedback for call 3 |
| `updateFlowFieldOn` | 9 | on-stack-replacement 4; wrong map 2 |
| `applyZombieFeet` area (zombie-feet.js 107, 113, 172) | 8 + 4 + 5 | dependent map was deprecated; wrong map |

| `resolveStaticProps`, `hordeFrame`, `syncZombieFogCull`, `tick` | 3 to 5 each | missing type feedback; one of each |

"Wrong map" and "map deprecated" mean the zombie object `z` changed shape after the optimized code was made for the old one: the game adds fields to a zombie after it is created (`z.lineSawBlock`, `z.hz`, `z.strafeDir`, `z.hzLungeT` ... all set in the walk, not at spawn). That is why `updateZombies` is rebuilt 62 times in 3 minutes (the Maglev count) and is the only hot function with that churn.

## Owners, worst first

1. **`updateZombies` and `zombieLateStep` (Grokbot, GB-251):** the only hot function over the limit as committed, the most deoptimized, and rebuilt 62 and 31 times. The split brings both under the limit and both reach TurboFan (about 55 s after their first call); what is left is the shape churn: give `z` all its fields when it is made (one object literal or a `makeZombie` that sets them, `null` or `0` until used), so its map stops changing.
2. **`tick` (index.html; the shell and the loop: Cursor and Claude):** 57,188 bytes, 3,700 from the limit, Maglev only. Splitting its phases into functions (as GB-251 does with `updateZombies`) keeps it clear of 61,440 and lets each part tier up.
3. **`updateMarinePose` (Claude), `holdWeapon` and `holdHand` (Grokbot), `apply` in studio/marine-turn.js (Cursor), `renderFrame` and `updateWorldAnimations` (Claude):** under the limit, not deoptimizing, Maglev only for 3 minutes; `holdHand` reached TurboFan at 114 s. I have no fix to name for them.
4. **Three's `render` and `_renderTransparents`:** Maglev only; no owner.
