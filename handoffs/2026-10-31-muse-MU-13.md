## 1. The frame the static world already lives in

Three per-frame systems touch *every* static group, whatever CL-288 does with bundles. They are the real interface a bundle has to fit:

- **`sceneCull()`** (index.html:2275) runs every frame in game (renderFrame, index.html:2398). It walks `scene.children` (expanding `cullKids` groups child-by-child, index.html:2296), and for each unit lazily measures a bounding sphere (`Box3.setFromObject`, at most 6 new spheres a frame, re-measured every 240 frames) then toggles visibility with `cullHide/cullShow` when the sphere is outside the frustum *and* beyond `SHADOW_HALF + 10` from the player (index.html:2284). Exempt: `cullSkip` set (player, marine, skyDome, cloudGroup, **groundSectors**, rainMesh, **house.group**, sun/hemi/camera, index.html:2246), `live` set, InstancedMesh, `frustumCulled === false`, and userData flags `effectPooled/pooled/shell/treeBatch/spans/noCull` (index.html:2307). So most static meshes are already visibility-toggled per frame by the CPU — a bundle recorded once cannot express "this cell hidden", which is the central tension in §3.
- **`updateSceneMatrices()`** (index.html:2373, CL-211) is the frame's one matrix walk: it skips cull-hidden, `visible === false`, `walkSkip` (batched trees) and descends `cullKids` groups only into shown children (index.html:2386). `renderFrame` then renders with `scene.matrixWorldAutoUpdate = false` (index.html:2408). Any group whose matrices are frozen (`matrixAutoUpdate = false`, world-space geometry at the origin) already costs nothing here — several groups below already are.
- **`sunShadowCadence()`** (index.html:2360) decides whether the shadow pass redraws at all (§4). By day it never skips; the static world's shadow cost is paid every frame in daylight.

The existing merge machinery: `bakeStatic` merges a group's still meshes **one mesh per material** (world/bake.js:12), skipping named/moving/instanced/skinned/morph/folded/vertex-coloured meshes; `foldStatic` goes further — every plain (untextured, opaque, non-glowing) MeshStandardMaterial mesh into **one mesh per (side, castShadow, receiveShadow)** with colour/roughness/metalness per vertex, drawn by a shared node material (world/bake.js:100ff, `foldMaterial`). Both run **once at build**; nothing re-runs them except the HQ/gun folds' own call sites. `?fold=0` (index.html:25707) and `?trees=single`, `?rockbatch=0`, `?foliage=legacy` are the existing A/B switches — CL-288's `?bundles=0` should follow the same pattern.

## 2. The groups

### 2.1 Terrain — ground wedges
- **Built:** `groundSectors` group (index.html:4734): 6 wedges × 3 bands (index.html:4738, `WEDGES = 6, BANDS = [1, 80, 170, TERRAIN_RINGS]`) = **18 meshes/draws**, each sharing `ground.geometry`'s attributes with its own index + hand-computed bounds (room for the shovel, ±14 m in y). `ground` itself stays, unseen, as the geometry keeper.
- **Touched after build:** the shared attributes are edited in place — the shovel, site levelling, terrain tint/wear (edits go through `ground.geometry` and set `needsUpdate` on position/color/gworn/gwear; e.g. the trapper excavation at index.html:4673ff and 4719ff) — so a wedge's *pixels* change without any mesh-level event. Exempt from sceneCull (in `cullSkip`, index.html:2246): visibility is three's own frustum culling per wedge via its bounds. Casts no shadow itself; receives.
- **Bundle:** needs a change first. The geometry is live-edited through shared attributes; a recorded bundle would either freeze the shovel/site edits or need invalidation on every attribute edit (they are bursty: dig, level a site, trapper excavation at build). Split candidate: bundle only the outer coarse band (past 170 m — never dug, never levelled), keep the inner two bands live. Confirm with GP-19996 whether an attribute `needsUpdate` inside a bundle replays or is skipped.

### 2.2 The HQ house (FOB) — baked + folded
- **Built:** `bakeStatic` over the house group with a `moving` skip set (shutter, intake tray, wired Hush board, fans, muzzle caps), then each hatch (`hq-cif`, `hq-armory`, `hq-skull-intake`, `hq-alarm-cabinet`) within itself, then each moving part within itself (index.html:25691–25698); then `foldStatic` over the same scopes with a `hold` set of runtime-changed materials (lamps, screens, buttons, LEDs, signs, glows) and `enter` for dressing (damaged terminal, tag wall, lockdown door) (index.html:25711–25716). Result: the house went from 145 draws (AG-91 census, cited index.html:25700) to one folded draw per (side × cast × receive) bucket + one baked mesh per surviving textured/glow material + the moving parts. `house.group.visible = false` until placed (index.html:25722).
- **Touched after build:** the moving set animates (fans spin, shutter, tray, muzzle caps); held materials change at runtime (lamp/screen/button colours — that's why they're held out of the fold); the tag wall's tags show when earned (kept separate, index.html:25710); the wired Hush board's visibility follows `hush.board` (index.html:25718); the whole group is sceneCull-exempt (index.html:2246) but matrix-walked. Cutaways: builds near the HQ fade via `updateRoofCutaway` (index.html:36360, per-build `_fade` → `applyFade`), and the radio vault / trapper cellar have their own `setCutaway` toggles (index.html:29402, 30716) — material/visibility changes on *other* groups, not the folded house, but the same pattern (a fade is a per-frame material touch) applies to anything folded that later needs fading.
- **Bundle:** needs a change first — split it. The folded static shell (walls, hatches' still parts) is bundle-ready once separated from: the moving set (never bundle — they animate), held materials (their uniforms/colours change; bundle only if GP-19996 says a material colour change replays), and anything the cutaway fades. The split already exists in code shape: `moving` + `hold` are exactly the two exclusion sets.

### 2.3 Landmarks — campsites, cabins, tower, graveyard, dock, bridges, sheds, wrecks, mast, fences
- **Built:** each landmark's parts are merged at build (`mergeParts`, e.g. `buildCampsite` index.html:5631: one merged mesh + ember + point light; cabins/tower/etc. likewise), registered in `landmarks` with colliders, hp, campfire. Draws: ~1 body draw per landmark (+ ember/light where present). The **FOB yard batch** (CL-280): yard landmarks' bodies are hidden and redrawn as **one world-space mesh** (`batchLandmarks`/`rebuildLandmarkBatch`, index.html:8939/8949; `fobBatch = batchLandmarks(fobLms, 'fob-yard-batch')`, index.html:26204; cast+receive shadow, index.html:8975).
- **Touched after build:** damage/destruction — `destroyLandmark` (index.html:8983) hides the mesh, rebuilds its batch (index.html:8983, 9102), kills light/ember/colliders; damage also marks `lm.batch.dirty` rebuilt once per frame batch (index.html:59333). Campfires light/douse (ember visibility, light intensity — per-frame in `updateCampfires`). Rosters/readables pinned to camps (MU-12 §4). The truck wreck carries the convoy dressing + headlight (MU-12 §2.5); the mast carries the relay lever/lockbox dressing. History props over the same ground are a separate `cullKids` group (CL-277: culled child-by-child, index.html:2296).
- **Bundle:** needs a change first. The landmark *bodies* are static between damage events, but destruction is a real runtime event and the batch rebuild pattern shows the intended grain: bundle per landmark (or keep the FOB-yard single batch as one bundle), invalidate/rebuild on `destroyLandmark` only. Campfire ember/light and mission dressing stay out. Never bundle: the ember/light, the relay lever, anything with a fade.

### 2.4 Trees — live meshes + batch cells (CL-10/CL-28)
- **Built:** each tree is a group of trunk/crown/branch/canopy meshes (`makeTree`; trunk cast+receive index.html:17634, canopy cast index.html:17853). `buildTreeBatches` (index.html:18193) copies every standing tree into **64 m cells: one wood mesh + one canopy mesh per cell** (index.html:18216ff), world-space, `matrixAutoUpdate = false`; the tree's own meshes hide and its matrices freeze (`tbFreeze`, `walkSkip`, index.html:18240ff). Batched cell meshes: `castShadow = false` (shadows stay with live trees near the player), wood receives (index.html:18220). Draws: 2 per occupied cell instead of ~4–8 per tree.
- **Touched after build — this is the busiest "static" group in the game:** `updateTreeBatches` runs **every frame** (index.html:18264): a snapshot diff (`tbSnapshot`, 20 fields: alive, falling, stump, log, leafHealth, health, burn, smoulder, trim, canopy transparency, visibility, parent, position, rotation, canopy scale, hidden leaves) over a third of batched trees per frame; changed or near trees go live (`tbGoLive`: collapse its vertex range in the cell, unfreeze, show own meshes), far unchanged trees rejoin (`tbGoBatch`: rewrite its range). Swaps capped at 12/frame. Felling, burning, chainsaw damage, canopy fade on the camera line — all funnel through the snapshot. Near the player (inside `SHADOW_NEAR + 4`, i.e. ~46 m) trees are live, so their shadows, sway and felling animate.
- **Bundle:** never as it stands; needs the CL-288 step-3 redesign first (the GPU forest: one instanced buffer per kind, compute-culled — board CL-288 item 3). A recorded bundle can't express per-tree range collapses/rewrites or the live/batch swap. What *could* bundle today: nothing in this group honestly — even far cells get range writes when a far tree burns or is felled by fire spread. Flag: if GP-19996 finds bundles support per-draw enable bits cheaply, cells could bundle with collapse-on-damage as the invalidation; otherwise this group waits for the instanced forest.

### 2.5 Rocks — live meshes + batch cells (CL-214)
- **Built:** `buildRockBatches` (index.html:17022): 147 rocks (index.html:16979 comment) merged **one mesh per 64 m ROCK_CELL** (index.html:16984), world-space, `matrixAutoUpdate = false`, cast+receive (index.html:17068 region); each rock's own mesh leaves the render layers (`layers.mask = 0`, `walkSkip`) but keeps its place/visibility state (`rockOwn`, index.html:16987). Draws: 1 per occupied cell.
- **Touched after build:** `updateRockBatches` **every frame** (index.html:17075): any batched rock now hidden/broken/removed goes live — its range collapses in the cell (`rockGoLive`, position attribute range write + `needsUpdate`). `damageRock` (index.html:17085) forces live, pulses scale via `setTimeout`, breaking removes the mesh and spawns chunks. Rebuilt wholesale on `resetGame` (index.html:59456, 61920).
- **Bundle:** needs a change first — and it's the cleanest candidate after terrain's outer band. Cells change only on rock damage/removal (rare, discrete). Options: bundle per cell with rebuild-on-`rockGoLive` (the rebuild code exists: `buildRockBatches`), or accept the collapse-write pattern inside a bundle if GP-19996 says attribute range updates replay. Either way the per-frame scan (147 visibility checks) can become event-driven from `damageRock`/hide call sites — worth doing with or without bundles.

### 2.6 Foliage chunks (ground cover)
- **Built:** `bakeFoliageChunks` (index.html:11289): tufts merged per **45 m cell** (`FOLIAGE_CELL`, index.html:11228), up to **2 chunks per cell** (shadow-casting bushes split from non-casting grass), one shared node material whose `positionNode` sways/tramples in the vertex shader from a per-vertex `sway` attribute (index.html:11237ff). Legacy per-tuft meshes were 1,746 of 2,745 draws (index.html:11227 comment); chunks are ~100 draws. Chunks sit at the origin in world space, `matrixAutoUpdate = false`, flagged `spans` (exempt from sceneCull, index.html:2307).
- **Touched after build:** **per frame, through uniforms, not meshes** — `foliageWind.time/dir/strength/player/tramplers` uniforms drive the sway and the player/zombie trample bend (index.html:11243ff); distance culling toggles chunk visibility every 4th frame (`cullFoliageByDistance`, index.html:11237); clearing (trapper yard, build sites) collapses tuft ranges to y=-500 (`clearFoliageInSquare`, index.html:11181) with `needsUpdate`; GFX preset changes flip `foliageCullDist`.
- **Bundle:** needs a change first, and the change is a question for GP-19996: if a bundle replays draws while the material's uniforms keep updating (uniforms live outside the recorded commands in r175's node system, plausibly yes), chunks bundle as-is *except* their visibility toggles — distance culling would need to move into the shader (discard by distance) or per-chunk bundles with enable toggles. The range-collapse clearing is rare/discrete (rebuild that chunk). If uniforms freeze at record time, this group never bundles until the sway is time-derived on GPU (it already is: `time` is the only per-frame scalar — a GPU clock uniform the bundle can't freeze would settle it).

### 2.7 Objective props, mission dressing, history props, caves, water, sky

Small win (~14 draws), do it only if the mechanism is already paid for elsewhere.
- **History props** (world/history-props.js, seated by index.html:8690ff): static meshes in a `cullKids` group. - **Caves/warrens:** mouths are terrain-adjacent static meshes; warrens build per entry and are not static (fights, passages). Mouths: bundle with terrain only if their aprons never edit — they do (cave apron wear in the ground attributes). Leave.

- **Player builds** (barricades, turrets, stairs…): not static — placed, damaged, repaired, faded by `updateRoofCutaway` (index.html:36360). **Never bundle.** Out of CL-288's scope by definition, listed so the census isn't misread: at night 20 these + zombies + effects are most of the remaining draws.

## 3. What a bundle would actually save here (honest sizing)

The frame is JS (D-104, AG-86): per draw ≈25 µs CPU (index.html:4737 comment). The static groups above total roughly: terrain 18 + HQ ~10 + landmarks ~15 + tree cells ~20 + live near trees (the expensive tail: each live tree is several draws + shadow) + rock cells ~10 + foliage ~100 + props/history ~50 ≈ **220–280 draws ≈ 5–7 ms of draw submission in daylight**, before zombies/builds/effects. But sceneCull already hides off-screen units and three frustum-culls the rest; the *submitted* count is what AG-170 measures (931–1193 by day includes everything). Bundles save the per-draw CPU walk (project, sort, bind) for recorded draws — they do not save vertex work. Biggest honest wins, in order: (1) foliage (~100 draws, one material, already world-frozen — if uniforms replay, this is the pilot); (2) history props + objective bases (many small draws, rarely touched); (3) rock cells + terrain outer band + landmark bodies (tens of draws, discrete invalidation); (4) HQ shell (few draws, already folded — small win, do last). Trees wait for the GPU forest; that's CL-288 step 3, not bundles.

## 4. The sun's shadow

- **Config:** one directional sun (index.html:2423), shadow map size from the GFX preset (index.html:2427, default 2048), camera near 1 / far 170, **±34 m box** (`SHADOW_HALF`, index.html:2435) that *travels with the player* (`sun.target.position.copy(player.position)`, index.html:59250, 60109), bias -0.0001, normalBias 1.4 (index.html:2443). The moon casts nothing.
- **Who casts:** everything with `castShadow` inside the 68 m box around him: live trees near him (trunk index.html:17634, crown wood, canopy index.html:17853 — batched cell meshes deliberately do not cast, index.html:18220, so past ~46 m trees lose shadows by design), rock batch cells (cast, index.html:17068 region) and live rocks, foliage bush chunks (grass chunks don't), landmark bodies + the FOB batch (index.html:8975), HQ folded/baked meshes (fold buckets keyed on castShadow, world/bake.js:100), objective props, builds, the marine (via the shadow proxy, `skinMergeGroup shadowOnly`, index.html:19732) and zombies/survivors. The ground only receives. Casters outside the box don't matter; casters *hidden by sceneCull* are kept in the shadow's radius (`shadowR = SHADOW_HALF + 10` keeps units visible for the shadow pass, index.html:2284).
- **Redraw today:** `sun.shadow.autoUpdate` is **true by day** (intensity ≥ 0.12: full shadow pass every frame, index.html:2362). Dusk/dawn (0.05–0.12): redraw every 4th frame (`SUN_SHADOW_NIGHT_EVERY`, index.html:2366). Deep night (< 0.05): redrawn once as night falls, then only when he has moved 16 m from where it was drawn, or every 900 frames (~15 s) (index.html:2367, CL-237 — each redraw is an ~8 ms spike that was setting the 1% low). Menu views centre the map on the menu focus (index.html:61089).
- **What moves in it, by day:** him, zombies, survivors, wildlife, falling/burning trees going live, builds being placed/damaged, doors/shutters/fans, smoke/fire effects that cast, the relay lift, vehicles' dressing — i.e. in daylight the map is *mostly* dynamic content inside a 68 m box, with the static casters (rocks, landmarks, HQ, near trees, props) as the unmoving majority of *triangles* but not of *changes*.
- **For CL-288's cached shadow:** the split the code already half-makes is static-vs-live trees at 46 m. A static-casters map (rocks, landmarks, HQ, terrain-adjacent props, *batched* tree cells if they were allowed to cast) could be redrawn only when: the sun's direction changes materially (time of day), the player crosses into a new map centre (the box rides with him — a cached map needs a fixed centre per tile, or redraw-on-16 m-move as deep night already does), or a static caster changes (rock broken, landmark destroyed, tree felled — all discrete events §2 already routes). The moving casters still need a per-frame map, but a small one (the 68 m box at 1024, or a tight box on the action). Whether r175 supports two shadow maps / a cached map without patching three is GP-19996's question; the game-side events needed to invalidate a static cache all exist and are enumerated above. Note the deep-night cadence already proves the visual tolerance: at sun 0.025 a 15 s-stale map is invisible; the same trick at dusk (0.05–0.12, every 4th) is the measured middle ground.
