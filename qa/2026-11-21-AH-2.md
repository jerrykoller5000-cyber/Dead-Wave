## Short Answer

- **WebGPU played normally (fresh launch, unloaded PC): INTERMITTENT — `0/3` froze in the clean fresh-profile batch (`~13.7s` shader warm-up), `0/2` froze on menu re-entry / 2nd tab, and `1/2` froze in our initial normal-play batch (`task-312` `webgpu-run2`, `index.html?solid=1`, `0.024%` 3D pixel change) when shader warm-up crossed `15.0s`.**
- **WebGL played normally (`?renderer=webgl`): NO — `0/3` froze (`86.6%–87.3%` 3D pixel change).**
- **Why it freezes whenever WebGPU warm-up takes >= 15.0s:** Normal cold WebGPU Training warm-up on the RTX 5080 takes **~13.6s–13.8s** inside `trainingWarmCompile()` (~16.7s total blackout including the ~3s room build) — only **1.2 seconds** below the `setTimeout(finish, 15000)` fallback timer (`index.html:69223`). Any run where stage-1 compile + `warmFrame('training-staged')` + `onSubmittedWorkDone()` takes **>= 15.0s** hits a race at `index.html:68758` and `69189–69197` that overwrites `postProcessing.render = () => {}` and skips `restorePPRender()`, freezing the 3D canvas permanently at `0 draws` on the `training-staged` warm-up frame (`qa/AH-2/webgpu-over15s-frozen-staged-frame.png`).

## 2. Claude 2's Two Ready-Frame Signals & Exact Root Cause in `index.html`

### A. Claude 2's Two Requested Values (Ready Training Frame, 20-RAF Window)
1. **`Boolean(window.DWOpening && window.DWOpening.active)`:** **`false`** on **every** run (`openingPhase: "menu"`, `openingHidden: true`, `flightHold: false`, `training.warming: false`) — **including on the frozen `task-312` `webgpu-run2` run**. So `tick()` is **not** returning early at `_titleReleased && window.DWOpening?.active` (`index.html:70817`).
2. **`TT.renderer._animation._animationLoop`:**
   - Present and non-null: `typeof === "function"`, `name === "tick"`.
   - On working WebGPU & WebGL runs (over 20 RAFs): `animLoopEntries = 20/20`, `renderer.render = 300` (15 passes/frame), `backend.draw = 6080–6100`, `gpuScopedValidationErr = null`.
   - On frozen runs (`AH-1` `#1`, `GP-20164`, `task-312` `webgpu-run2`): `tick()` **still runs at 60 FPS** all the way past `renderFrame()` (updating `#perf` to `fps 60 · draws 0 · tris 0k` and updating DOM HUD reticles/prompts), while **`renderer.render` is called `0` times**.

### B. Exact Code Bug (`index.html:68757–68760` & `69142–69223` inside `trainingWarmCompile`)
1. `trainingWarmCompile()` starts a hard 15-second fallback timer at `index.html:69223`: `setTimeout(finish, 15000)`.
2. Stage 1 compiles ~200 WebGPU pipelines (`pCompile = compileForLiveTarget()` at `69142`), renders **`warmFrame('training-staged')`** at `69146` (which puts `cutawayKeepers` — the Skull Window frame & heads — on the Firing Line and 6 warm-up guns on the marine), and awaits `renderer.backend?.device?.queue?.onSubmittedWorkDone?.()` at `69147`.
3. When Stage 1 finishes in **< 15.0s** (~13.7s on an unloaded RTX 5080), Stage 2 runs `restorePPRender()`, draws `warmFrame('training-clean')`, and calls `finish()` cleanly.
4. **When Stage 1 takes >= 15.0s** (just 1.3s slower due to cold D3D11/FXC compile jitter, prior title/tab GPU work as in `GP-20164` or `task-312` Run 2, or any slower GPU):
   - At `15.0s`, `setTimeout(finish, 15000)` fires `finish()`, setting **`done = true`** while `origPPRender` is still `null`, re-attaching `setAnimationLoop(tick)`, and lifting `#trainingBlackout`.
   - Moments later, Stage 1 finishes `finally` cleanup and **runs lines `69189–69191` without checking `if (!done)`**:
     ```js
     if (postProcessing && !origPPRender) {
       origPPRender = postProcessing.render;
       postProcessing.render = () => {};
     }
     ```
   - Immediately in the next `.then(...)` at **line `69196`**:
     ```js
     if (done || !training.active) { finish(); return; }
     restorePPRender();
     ```
     Because `done` is already `true`, `finish()` hits `if (done) return;` at **line `68758` BEFORE `restorePPRender()` at line `68760`**, and line `69196` returns **BEFORE `restorePPRender()` at line `69197`**!
   - **`postProcessing.render` stays stuck as `() => {}` forever.** Every subsequent `tick()` calls `renderFrame()` -> `postProcessing.render()` (no-op), producing `0` `renderer.render()` calls and leaving `warmFrame('training-staged')` frozen on screen.
